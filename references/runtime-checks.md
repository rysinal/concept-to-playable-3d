# 实机、交互和性能

## 让画面对照可复现

复用已有调试场景/存档；必要时增加最小的开发用场景入口，记录相机、种子、时间、天气和对象状态。比较前后截图时使用相同条件。测试入口可用于准备状态，但不能代替真实输入验证整条玩法路径。

当前检查覆盖游戏需求中的适用项即可：

- 启动进入实际场景；资源加载完成，无阻断异常。
- 真实输入触发移动/转向/目标动作，角色有正确状态变化和可见反馈。
- 与地形、障碍或交互物的关系正确；失败/成功及重新开始能实际走通。
- 旋转/跟随镜头及连续运动中检查闪烁、穿模、阴影跳动、卡顿。

## 60fps 要如何描述

60fps 对应约 16.67ms 帧预算，是待验证目标，不是某次输出的承诺。帧间隔包含显示调度影响，不能直接叫作 GPU 渲染耗时。

对小型 demo 可在资源与着色器预热后，前台运行一段代表性玩法（例如 30 秒）。记录实际时长和样本数，不把此例硬设为所有项目的充分测试标准。

至少记录：

- 硬件/OS、引擎或浏览器版本、WebGL/WebGPU 等后端；软件渲染需单独标注。
- 视口、实际 drawing buffer 分辨率、DPR、质量档、是否动态分辨率。
- 场景/动作/预热条件、帧数和采样时间；平均 FPS 用有效帧间隔总数除以总时长计算。
- 帧间隔中位数、P95/P99、明显长帧；首次加载/编译卡顿单独说明。
- 能获得的 draw calls、三角形和纹理/几何计数。未取得的指标写 unknown。

前后比较保持硬件、场景和画质条件一致。headless + SwiftShader 的结果只能描述该环境的趋势；截图、仅统计 rAF 回调或主观流畅不证明目标硬件稳定 60fps。接近刷新率的帧间隔需考虑调度抖动，不用单一 16.67ms 硬阈值机械判定。

Three.js 多 pass 渲染时检查 `renderer.info` 是否统计整个帧；默认每次 render 重置可能漏计后处理。应按当前版本 API 在整帧结束处收集/重置。计数减少本身不等于帧率已改善。

## 有证据再优化

| 现象/测量 | 优先检查 |
| --- | --- |
| draw calls 多 | 重复对象实例化、材质批次、可合并的静态对象 |
| GPU/像素负担明显 | 阴影范围和分辨率、透明叠加、后处理、drawing buffer |
| CPU 卡顿 | 每帧分配、重复遍历、物理/输入时序、主线程资源工作 |
| 加载切换卡顿 | 着色器预热、上传时机、分批工作、资源缓存 |

不要仅凭 FPS 低猜瓶颈。先取得 profiler 或有控制的开关对比，再做最小改动。优化后重新检查截图和核心动作，报告任何画质档位变化。
